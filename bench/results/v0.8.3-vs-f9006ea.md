# eulix v0.8.3 vs `f9006ea` (v0.9.0 candidate)

The first full run of the version benchmark, comparing the v0.8.3 release with `dev` at `f9006ea`, the commit that becomes v0.9.0.

Overall, `f9006ea` is better where it matters and has no blocking regression:

- **Retrieval improved.** The expected file now comes first for 13 of 21 code questions, up from 8, and appears in the top 5 for 18, up from 8.
- **The parser improved.** It links method calls (PRISM-2 is partly fixed) and its output is now identical from run to run.
- **Indexing on the GPU is 18 to 64% slower.** This is the cost of a correctness fix: v0.8.3 embedded truncated chunks.
- **Plain-language questions still fail** in both versions (EMB-3).

### Why GPU indexing is slower

The slowdown was traced, by timing every `eulix-embed` commit since v0.8.3 on this repo's `kb.json`, to **`685d011` "fix(pipeline): measure true token lengths"**. It is a correctness fix:

- **Bucketing:** on the GPU, chunks are grouped into fixed-length buckets (32 to 512 tokens), and each batch is padded *and truncated* to its bucket.
- **v0.8.3 guessed lengths:** it estimated a chunk's length as `len(text) // 4`. Code averages 2.6 characters per token, so most chunks went into a bucket shorter than their real length.
- **What v0.8.3 lost:** 67% of chunks were cut short, losing a median 18% of their text and up to 48%.
- **Effect on vectors:** those chunks got different vectors from their full text: cosine median 0.992, 5th percentile 0.938, worst 0.897.
- **The cost of the fix:** f9006ea counts tokens with the real tokenizer, so it sends 1.47 times as many tokens through the model. That matches the 1.47 times lower throughput (564 → 384 chunks per second on this repo).
- **CPU:** CPU runs don't use buckets, so neither version truncates there. Both embed about 26 chunks per second on CPU.

The larger chunk counts on flask (+72%) and ripgrep (+13%) come from the parser finding more functions (see parser quality); the index grows with them.

## Parser quality

From the index that `eulix analyze` built. "Methods with a caller" is the share of method nodes that at least one call edge points to.

| Corpus | Nodes | Call edges | Methods with a caller | Cross-language edges | Identical across runs |
| --- | --- | --- | --- | --- | --- |
| eulix | 2,760 → 2,818 | 2,877 → 3,468 (+21%) | 0% → 52.8% | 239 → 106 | bytes no → yes |
| flask | 818 → 1,469 | 515 → 582 | 0% → 22.9% | 0 → 0 | bytes no → yes |
| gin | 1,495 → 1,495 | 1,896 → 1,896 | 0% → 0% | 0 → 0 | bytes no → yes |
| ripgrep | 2,368 → 2,686 | 482 → 1,025 (+113%) | 0% → 17.8% | 0 → 0 | bytes no → yes |
| gson | 1,063 → 1,063 | **0 → 0** | 0% → 0% | 0 → 0 | bytes no → yes |
| Linux | 784,530 → 786,533 | 1,531,425 → 1,527,404 | 0% → 22.9% | 73,958 → 69,890 | not checked |

No file failed to parse in either version.

- **Determinism.** f9006ea's output is byte-identical between runs. v0.8.3's has the same content (nodes and edges match), but its bytes vary from run to run because the call graph's tags are written from a `HashMap`.
- **Methods now get callers in Python and Rust.** eulix (Rust and Python methods), flask and ripgrep gained method edges. This is the receiver-aware resolution for PRISM-2.
- **Go and Java still get no method edges.** gin stays at 0%, and on eulix all 301 Go methods have no caller. gson has no call edges at all in either version. These are the open [PRISM-2 and PRISM-5](../../docs/Known-Issues/Parser-And-PRISM.md) issues (Go and Java receivers never reach the resolver), now confirmed on real projects.
- **Fewer false cross-language edges.** They fell from 239 to 106 on eulix (PRISM-4).
- **The kernel still parses half its files only partly** in both versions (PARSE-3: C macros).

## Known limits of this run

- **Plain-language retrieval is broken in both versions:** 0 or 1 of 8 ranked first, even with correct CPU vectors. ROCm (EMB-1) is not the cause. The chunk text the vectors are built from carries only names and signatures (EMB-3).
- **Small question set:** with 29 questions, one question moves "ranked first" by 3.4 points. 31 more questions are drafted in `bench/suite/questions/eulix-draft.toml`, pending review.
- **Older baselines aren't comparable:** the 14 to 15 of 21 recorded in `.eulix/eval/` came from an index that still contained the question list itself (`scripts/eval_mcp.py`). This corpus excludes it.
- **Single runs:** the kernel run and the query memory figures are single runs; their flags have no spread to compare.
