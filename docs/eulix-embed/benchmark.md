## What to Benchmark

There are three distinct performance surfaces worth measuring separately:

| Surface                 | What it tells you                                         |
| ----------------------- | --------------------------------------------------------- |
| **Pipeline throughput** | End-to-end chunks/sec for a given backend + model         |
| **Inference latency**   | Single-embedding round-trip time (tokenize → ONNX → pool) |
| **Index I/O**           | Save/load speed and file size for JSON vs. binary formats |

---

## Prerequisites

```bash
# Build in release mode (mandatory — debug is ~10× slower)
cargo build --release

# Confirm your backend is detected correctly
./target/release/eulix_embed embed --help

# For CUDA: verify nvidia-smi is reachable
nvidia-smi

# For ROCm: verify rocm-smi is reachable
rocm-smi
```

Have a representative `knowledge_base.json` ready. If you don't have one, generate a small synthetic one or use the Eulix parser on any open source project.

## 1. Pipeline Throughput

The pipeline already prints per-step timing and a chunks/sec rate. The quickest benchmark is a direct run:

```bash
time ./target/release/eulix_embed embed \
  -k knowledge_base.json \
  -o ./bench_output \
  -m sentence-transformers/all-MiniLM-L6-v2
```

The stdout output includes:

```
Processing N chunks in batches...
  Progress: 100/500 (142.3 chunks/sec, ETA: 3s)
✓ Completed all embeddings in 4.21s
   Average: 118.8 chunks/sec
```

**Run at least 3 times** and take the median — the first run downloads and caches the model, so it's always an outlier.

To compare backends explicitly:

```bash
# CPU baseline
EULIX_BACKEND=cpu ./target/release/eulix_embed embed -k kb.json -o ./out_cpu

# CUDA (if available)
EULIX_BACKEND=cuda ./target/release/eulix_embed embed -k kb.json -o ./out_cuda

# Dummy (measures pipeline overhead without inference cost)
EULIX_BACKEND=dummy ./target/release/eulix_embed embed -k kb.json -o ./out_dummy
```

The dummy run gives you a lower-bound for chunking + I/O overhead, letting you isolate inference cost:

```
inference_time = total_time(cpu_run) - total_time(dummy_run)
```

## 2. Inference Latency (Single Query)

Use the `query` subcommand to measure single-embedding latency:

```bash
# Warm up (model download + JIT compilation)
./target/release/eulix_embed query -q "warm up" > /dev/null

# Measure 10 queries
for i in $(seq 1 10); do
  time ./target/release/eulix_embed query \
    -q "how does authentication work" \
    -m sentence-transformers/all-MiniLM-L6-v2 \
    > /dev/null
done
```

Or use `hyperfine` for cleaner stats:

```bash
# Install: cargo install hyperfine
hyperfine --warmup 3 --runs 20 \
  './target/release/eulix_embed query -q "authentication flow" > /dev/null'
```

Sample output:

```
Benchmark 1: ./target/release/eulix_embed query ...
  Time (mean ± σ): 38.2 ms ± 1.4 ms
  Range (min … max): 36.1 ms … 42.8 ms
```

> Note: each invocation initializes a new ONNX session. For production latency, measure from an already-initialized `QueryEmbedder` in a long-running process instead.

## 3. Index I/O Speed

Measure save and load times for the JSON and binary formats:

```bash
# After a pipeline run, benchmark load times
hyperfine --warmup 2 \
  'python3 -c "import json; json.load(open(\"./bench_output/embeddings.json\"))"' \
  'python3 -c "
import struct, numpy as np
with open(\"./bench_output/embeddings.bin\",\"rb\") as f:
    magic=f.read(4); ver=struct.unpack(\"<I\",f.read(4))[0]
    ml=struct.unpack(\"<I\",f.read(4))[0]; f.read(ml)
    count=struct.unpack(\"<I\",f.read(4))[0]
    dim=struct.unpack(\"<I\",f.read(4))[0]
    np.frombuffer(f.read(count*dim*4),dtype=\"<f4\")
"'
```

For the Rust side, add a criterion benchmark or use the built-in `compare` subcommand to verify correctness after a format conversion:

```bash
./target/release/eulix_embed compare \
  ./bench_output/embeddings.json \
  ./bench_output/embeddings.bin
```

## 4. Model Comparison

Run the same KB through different models and compare throughput vs. quality:

```bash
for model in \
  "sentence-transformers/all-MiniLM-L6-v2" \
  "BAAI/bge-small-en-v1.5" \
  "BAAI/bge-base-en-v1.5"; do
  echo "=== $model ==="
  time ./target/release/eulix_embed embed \
    -k knowledge_base.json \
    -o "./bench_$(basename $model)" \
    -m "$model"
  echo ""
done
```

Record the `Average: N chunks/sec` line from each run and the output file sizes:

```bash
du -sh ./bench_*/embeddings.bin
```

## 5. Parallel vs. Sequential

The embedder exposes both `generate_vectors()` (sequential batches) and `generate_vectors_parallel()` (Rayon par_iter). To benchmark the parallel path, temporarily swap the call in `main.rs` and rebuild:

```rust
// In EmbeddingPipeline::process(), replace:
let vector_store = self.generator.generate_vectors(chunks.clone())?;
// with:
let vector_store = self.generator.generate_vectors_parallel(chunks.clone())?;
```

```bash
cargo build --release
time ./target/release/eulix_embed embed -k knowledge_base.json -o ./bench_parallel
```

The parallel path is generally faster on CPU with many cores and slower on GPU (where batch inference already saturates the device).

## Profiling (optional)

For deeper analysis, use `cargo flamegraph`:

```bash
cargo install flamegraph
sudo cargo flamegraph --release -- embed -k knowledge_base.json -o ./out
# Opens flamegraph.svg in browser
```

Or `perf` directly:

```bash
perf stat ./target/release/eulix_embed embed -k knowledge_base.json -o ./out
```

Hot paths to look for: tokenization loop in `onnx_backend.rs`, the mean-pooling reduction, and JSON serialization in `index.rs::save()`.
